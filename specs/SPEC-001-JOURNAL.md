# SPEC-001 — Journal and Projections

**Status:** Draft for implementation
**Depends on:** nothing
**Depended on by:** SPEC-002 (PDP/PEP), SPEC-003 (Turn Executor)

---

## 1. Purpose

The Journal is the single primary store in the Apex Runtime. Every fact about what
has happened — user messages, model output, policy decisions, tool effects, agent
lifecycle, artifact activation — exists as an event in the Journal.

All other queryable state (Ledger, Corpus, pending approvals, challenge counters)
is a **projection**: a derived, disposable structure rebuildable by replaying the
Journal. Projections may be dropped and rebuilt at any time without data loss.

This is the property that makes rollback, audit, replay-based testing, and schema
evolution tractable. It is the one architectural commitment that must not be
compromised for convenience.

## 2. Responsibilities

The Journal component:

- assigns event identity and ordering
- validates every event against its registered payload schema
- appends events durably and atomically
- maintains a tamper-evident hash chain
- exposes replay over ranges and filters
- hosts the projection rebuild mechanism

## 3. Boundaries

The Journal does **not**:

- make policy decisions (SPEC-002)
- call models or tools (SPEC-003)
- delete or mutate events, ever, for any reason including correction
- interpret payload semantics beyond schema validation

There is no `UPDATE` and no `DELETE` against the event table. Corrections are new
events that supersede earlier ones. Enforce this at the storage layer, not by
convention: the application role must lack those grants.

## 4. Event envelope

Every event carries the same envelope. No exceptions, no per-type variation.

| Field | Type | Notes |
|---|---|---|
| `event_id` | ULID | Monotonic, lexicographically sortable, generated by Journal |
| `seq` | int64 | Dense sequence, assigned on append, gap-free |
| `ts` | UTC ISO-8601 | Runtime clock at append time |
| `actor` | string | `user` \| `apex` \| `agent:{agent_id}` \| `system` |
| `type` | string | Namespaced, dotted; must be in the type registry |
| `schema_version` | int | Payload schema version for this type |
| `session_id` | ULID \| null | Groups a conversational or scheduled session |
| `turn_id` | ULID \| null | Groups all events produced by one turn |
| `caused_by` | ULID \| null | Event that directly caused this one |
| `payload` | JSON | Validated against `(type, schema_version)` |
| `prev_hash` | hex | SHA-256 of previous event's `hash` |
| `hash` | hex | SHA-256 over canonical serialization of all fields above |

`caused_by` gives a causal chain distinct from time order. "Why did this tool run?"
must be answerable by walking `caused_by` back to a user message or a schedule tick.

### 4.1 Hash chain

`hash = SHA256(canonical_json({event_id, seq, ts, actor, type, schema_version,
session_id, turn_id, caused_by, payload, prev_hash}))`

Canonical serialization: UTF-8, sorted keys, no insignificant whitespace.

The chain makes silent tampering detectable. It does not make it impossible — an
attacker with write access can rewrite the whole chain. Detection requires
periodically anchoring the head hash somewhere outside the Realm (printed, emailed,
committed to a separate repo). Treat that as an operational task, not a code
feature, and document that unanchored chains are integrity checks against
corruption and bugs, not against a determined adversary with disk access.

## 5. Event type registry

Types are registered statically in code with a JSON Schema per version. Appending
an unregistered type is an error, not a warning.

Minimum registry for the first working turn:

```
session.started              session.ended
turn.started                 turn.completed        turn.aborted
user.message                 apex.message
model.called                 model.returned        model.failed
tool.requested               tool.result           tool.failed
policy.decided               policy.challenged
approval.requested           approval.granted      approval.denied
                             approval.expired
memory.assertion.proposed    memory.assertion.applied
                             memory.assertion.rejected
commitment.created           commitment.updated    commitment.closed

artifact.proposed            artifact.validated    artifact.rejected
artifact.evaluated           artifact.activated    artifact.rolled_back
bundle.revoked               approval.invalidated  model.qualified

reflection.started           reflection.completed
self_model.digest.regenerated
voice.envelope.measured      continuity.evaluated  development.reviewed
admin.action
```

Deliberately absent from v1: agent lifecycle, deployment, canary events. Add them
when the agent framework is specified, not before.

Governance event payloads are defined in SPEC-004. Note that `artifact.rejected`
and `artifact.rolled_back` are journaled with the same weight as successful
activations — a governance trail that records only successes cannot answer "what
did we try to activate and why did it fail?", which is the question incidents
actually raise.

### 5.1 Schema evolution

Payload schemas are additive within a `schema_version`. Breaking changes increment
the version, and **old versions remain supported in the replay path forever**. This
is the cost of an append-only log and it is not optional; a projection that cannot
replay a 2026 event is a projection that cannot be rebuilt.

## 6. Projections

| Projection | Derived from | Purpose |
|---|---|---|
| **Ledger** | `commitment.*` | Current state of every commitment: `open`, `met`, `broken`, `cancelled`, with due dates and owner |
| **Corpus** | `memory.assertion.applied` | Durable facts, preferences, lessons, with provenance and supersession |
| **Pending approvals** | `approval.*` | Open confirm-tier requests and their expiry |
| **Challenge counters** | `policy.challenged` | Counts per rule per policy version, for rate limiting and telemetry |
| **Working set index** | Corpus + Ledger + recent Journal | Retrieval surface for SPEC-003 |

### 6.1 Rules

1. A projection is a **pure fold** over the Journal. Same events in, same
   projection out, on any machine, at any time.
2. Projections store `last_applied_seq`. Rebuild = truncate, replay from 0.
3. No projection is authoritative. If a projection disagrees with the Journal,
   the projection is wrong.
4. Projections may be rebuilt online; readers tolerate a lagging
   `last_applied_seq`.

### 6.2 Corpus specifics

Each Corpus entry:

```
entry_id, subject, predicate, value, confidence,
asserted_by_event, supersedes (entry_id | null),
superseded_by (entry_id | null), pinned_version
```

Entries are never deleted. Contradiction is expressed by supersession, which
preserves the history of what Apex believed and when — the difference between an
intelligence that learns and one that silently rewrites its own past.

**The model never writes the Corpus.** It emits `memory.assertion.proposed`. A
deterministic writer validates (schema, subject known, confidence in range, no
self-referential grants) and emits `applied` or `rejected`. This is the same
decide/enforce split as SPEC-002, applied to memory.

### 6.3 Self-assertions

Entries carry `subject_class: world | self`. The `self` space is the **Self-Model**
(SPEC-005): Apex's accumulated, experience-authored self-description.

Two additional validation rules apply to `subject_class: self`:

1. **Evidence required.** The assertion must cite one or more `evidence_events`
   already present in the Journal. Self-assertions without grounding are rejected.
   A model writing unevidenced claims about its own past will confabulate one, and
   confabulated self-narrative compounds — each ungrounded claim becomes context
   supporting the next.
2. **Protected dimensions.** Assertions whose predicate falls in the Identity
   Core's protected set — values, constitutional stance, relational role, authority,
   name, nature — are rejected regardless of evidence. Apex may revise who he is
   becoming; he may not revise what he must remain.

Rejections are journaled with the failing rule. A rejection stream that trends
toward the protected set is a meaningful signal and should be visible on the
control plane.

## 7. Storage

**SQLite for v1.** Single tenant, single writer, transactional append, trivial
backup, zero operational surface.

Reject Postgres, Kafka, and event-store products at this stage. They solve
multi-writer and multi-consumer problems this system does not have, and each adds
a daemon to operate before Apex has completed a single useful task. SQLite's
limits (~1 writer, low-hundreds of TPS with WAL) are two to three orders of
magnitude above the load of one human and one intelligence.

The storage interface is narrow enough (`append`, `read_range`, `head`) that
replacement later is a day of work if load ever justifies it.

Configuration: WAL mode, `synchronous = FULL`, one connection for writes.

## 8. Interface

```
append(actor, type, payload, *, session_id=None, turn_id=None,
       caused_by=None) -> Event
    Validates, assigns event_id/seq/ts/hashes, writes, returns the event.
    Atomic. Raises on schema violation. Never partially writes.

read_range(from_seq, to_seq=None, types=None, session_id=None,
           turn_id=None) -> Iterator[Event]
    Ordered by seq ascending.

head() -> (seq, hash)

verify_chain(from_seq=0, to_seq=None) -> ChainReport
    Recomputes hashes; reports first divergence.

rebuild(projection_name) -> RebuildReport
```

## 9. Acceptance criteria

1. Appending an event with an unregistered `type` fails.
2. Appending a payload violating its registered schema fails.
3. `seq` values are dense and gap-free across process restarts.
4. The database role used by the application cannot execute `UPDATE` or `DELETE`
   on the events table; a test asserts this by attempting both.
5. `verify_chain` detects a single mutated payload byte and reports the exact `seq`.
6. Dropping and rebuilding every projection from an empty state reproduces
   byte-identical projection contents.
7. Killing the process mid-append leaves the Journal valid, with either the full
   event present or absent — never a partial row and never a broken chain.
8. Given a `tool.result` event, walking `caused_by` reaches the originating
   `user.message` or schedule tick.
9. A Corpus entry can never be removed; superseding produces two entries linked
   in both directions.
10. `memory.assertion.proposed` alone never alters the Corpus.

## 10. Testing considerations

- **Property test:** for random event sequences, `replay(events)` is deterministic
  and order-independent of wall-clock time.
- **Golden replay:** a checked-in fixture Journal with an expected projection
  snapshot. Any change to projection logic that alters the snapshot must be an
  explicit, reviewed diff. This is your regression net for memory semantics.
- **Crash injection:** kill at randomized points during append; assert invariants
  in criterion 7.
- **Schema graveyard:** the fixture Journal must contain at least one event at
  `schema_version = 1` for a type later bumped to 2, so the old-version replay
  path stays exercised.
- **Volume:** 1M synthetic events; assert full rebuild completes in a duration you
  are willing to wait during an incident. If it does not, add projection
  snapshotting — do not change stores.
